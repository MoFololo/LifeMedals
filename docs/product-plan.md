# 人生勋章 App —— 产品与技术计划书

---

## 1. 核心洞察

游戏里做完一件事有动力，是因为有明确的奖励和成就感；日常 To Do 打个勾，反馈太弱了。

我想做的这个 App，就是把"游戏化反馈"接到"真实生活任务"上，靠三样东西实现：

1. **契约化**：把模糊的想法变成一份 AI 生成、用户确认的"任务契约"（标题、截止时间、验收标准、所属勋章）。
2. **证据化**：完成不是自我声明，而是提交证据，由 AI 核验。
3. **积累化**：每次验证通过都沉淀成经验值和可回顾的成就档案，而不是消失在已完成列表里。

---

## 2. 产品思路

差异化不能停留在"AI 查截图"这件事本身，而要落在**可验证的成就积累**上——这是勋章系统真正要解决的问题。

三态核验结果（Verified / Need More Proof / Not Verified）比强行二选一更合理，能减少"被机器人冤枉"的挫败感。

MVP 先服务一类高粘性用户（在校/求职学生），比一开始做"管理所有人的所有目标"更容易做出手感。第一版不做金钱惩罚、社交排行榜、复杂防作弊——这些都是"以后再说"的功能，现在加只会拖慢进度。

**一句话生成任务契约 + 生成后可编辑确认**，是这个产品的核心体验：用户不仅能同意 AI 生成的契约，还能改时间、改标题、改所属勋章。这样即使 AI 生成得不够准，用户也能在执行前修正，而不是执行后才发现契约不合理。这一点要作为核心体验重点打磨。

**勋章 + EXP 系统**是把"身份空间"（Builder / Problem Solver / Athlete...）具象化、可量化的方式：

> 身份空间 = 勋章类别，完成任务 = 经验值，长期积累 = 等级/称号

这样"过去三个月我完成了 46 道算法题、去了 18 次健身房"这种长期身份感，就自然由勋章等级呈现出来，不需要额外做一套统计页面。

关于"证据设计要轻量"——**这不是为了防作弊，而是为了不让提交证据这件事本身变成新的拖延源**。比如健身任务，与其要求前后两张自拍，不如允许一张训练记录截图或 Apple Health 截图。轻量的证据要求，本质上是留存率问题，不是诚信问题。

## 3. 核心产品闭环

```
说一句话 → AI生成任务契约(可编辑) → 用户确认 → 执行 → 提交证据 → AI核验 → 勋章+EXP → 存入Library
```

示例：

用户输入：`明天晚上10点前做两道LeetCode Medium`

AI 生成（可编辑）：
- 标题：完成两道 LeetCode Medium
- 截止时间：明天 22:00
- 验收标准：提交两张 Accepted 页面截图，需可见题目名称、难度、Accepted 状态
- 所属勋章：Problem Solver（+40 XP）

用户点"确认"（或先改动时间/勋章再确认）→ 执行 → 上传截图 → AI 判定 Verified → 生成成就卡，Problem Solver 勋章 +40 XP，加入 Library。

## 4. 勋章与成长系统设计

### 4.1 默认勋章类别（可让用户自定义新增）
| 勋章 | 对应场景 |
|---|---|
| Problem Solver | LeetCode、考试、刷题 |
| Builder | 项目开发、发布 |
| Career | 投简历、面试准备 |
| Athlete | 健身、跑步、运动 |
| Scholar | 课程学习、阅读 |
| Life Admin | 订票、缴费、预约（v1 暂不做，见下文隐私提示） |

### 4.2 三层反馈
1. **即时反馈**：验证通过动画 + 具体反馈文案（"你今天完成了两道Medium，其中一道是动态规划，这是你本周第5道题"）+ EXP 到账动画。
2. **短期反馈**：首页展示本周各勋章完成率、连续完成天数（streak）、比上周多做了什么。
3. **长期反馈**：勋章等级/称号（如 Problem Solver Lv.5"算法学徒"），以及可回顾的成就时间线。

### 4.3 等级机制
- 每个勋章独立计算 EXP 和等级，避免"一个类别刷经验，另一个类别荒废"却显得整体等级很高的失真感。
- 等级曲线不需要复杂，线性递增（每级所需 EXP 略微提高）即可，重点是"看得见进度条"，不是数值精妙。

## 5. MVP 范围

### v1 做的四类任务（证据形态清晰、我自己就是种子用户）
1. LeetCode / 课程学习
2. 项目开发
3. 投递求职申请
4. 健身 / 运动

### v1 暂不做
- 订机票等涉及姓名、订单号、支付信息的任务（隐私/合规风险，且证据形态复杂）——可以作为 v1.x 的加分项，不必完全排除，只是不放进第一版
- 复杂防作弊机制（GPS、实时拍摄水印等）
- 社交排行榜、好友监督
- 金钱惩罚
- 通用 AI 聊天助手功能

## 6. 技术方案

### 6.1 客户端：SwiftUI（Mac 优先，iOS 复用）

先做 Mac 软件、再做 iOS App 这条路径下，**SwiftUI 是明显最优选择**，原因：

- 一套 Swift 代码库，通过 SwiftUI 的自适应布局，macOS 和 iOS target 可以共享绝大部分业务逻辑和 UI 代码，只在少数地方做平台适配（比如 Mac 用侧边栏导航，iPhone 用 TabView）。
- 原生体验：可以直接用系统的通知、图片选择器（PhotosPicker）、Vision 框架（本地做初步 OCR/图像预处理，减少调用 AI 的次数和成本）、快捷指令（Shortcuts）等，"用着方便"这个诉求原生实现比网页/Electron 更容易达到。
- 天然对接 Mac App Store 和 iOS App Store 的分发路径，不需要中途换技术栈。
- 用 Swift Concurrency（async/await）处理"提交证据 → 调用后端 → 等待AI核验"这类异步流程，代码简洁。

不做 Electron / 网页套壳：不是网页产品，而且 Electron 做出来的 Mac 应用在系统集成和体验上天然弱于原生 SwiftUI。

### 6.2 后端：两条路径，先走快速路径

因为 AI 需要调用 Claude API（不能把 API Key 放进客户端），并且要存储任务、图片、勋章数据，需要一个后端。两个选项：

**方案A（先做这个，能最快跑通产品）：Supabase**
- Postgres 数据库 + 内置 Auth（登录注册）+ Storage（存截图）+ Edge Functions（Deno/TypeScript，用来调用 Claude API）
- 优点：不用自己搭鉴权、不用自己管数据库运维，几天内就能把"提交截图→触发AI核验→写回结果"这条链路跑通
- 缺点：作为求职作品集，"深度"不如自建后端

**方案B（如果想在简历上体现完整后端工程能力，可以在方案A跑通产品逻辑后，逐步替换）：**
- 后端：Python FastAPI 或 Node.js（Express/NestJS）
- 数据库：PostgreSQL
- 队列：Redis + 任务队列（处理"异步AI核验、失败重试"，是很好的加分点）
- 存储：Cloudflare R2 或 AWS S3（存截图）
- 部署：Railway / Fly.io / Render

**做法**：先用方案A把产品做出来、自己用起来、验证核心体验是否真的有动力感；如果产品验证成立且后续要用它做求职作品集，再把核心服务迁移到方案B，顺便积累"重构一个真实产品的后端"这种更有说服力的经历。

### 6.3 AI 调用：Claude API，两类场景

1. **任务契约生成**（文本→结构化 JSON）
   - 输入用户一句话，要求 Claude 严格按 JSON 格式输出 `{title, deadline, evidence_requirement, suggested_badge, suggested_xp}`
   - 客户端渲染成可编辑表单，用户改完后再确认

2. **证据核验**（多模态：图片+已确认的验收标准）
   - 把用户提交的截图 + 之前确认的验收标准一起发给 Claude
   - 要求返回 `{verdict: "Verified"|"Need More Proof"|"Not Verified", explanation}`
   - **关键原则**：验收标准必须在任务确认时就锁定，AI 核验阶段不能"临时改规则"，否则用户会觉得被不讲理地拒绝

### 6.4 核心数据表（简要）

- `users`：用户基础信息
- `badge_categories`：勋章类别（Problem Solver / Builder / Athlete...），支持用户自定义
- `user_badges`：每个用户每个类别的当前 EXP、等级
- `tasks`：任务契约（标题、截止时间、验收标准、所属勋章、状态）
- `evidence`：提交的证据（图片链接、AI判定结果、解释、提交时间）
- `xp_logs`：每次 EXP 变动记录（关联任务，方便做"本周完成了什么"的统计）

### 6.5 图片存储
Supabase Storage（方案A）或 Cloudflare R2（方案B），成就卡本身可以按需动态生成，不必存成图片文件，省存储成本。

## 7. 分步开发路线图

**Step 0：环境搭建**
建 Xcode 项目（macOS App target）；注册 Supabase 项目；申请 Anthropic API Key（放在后端 Edge Function 环境变量里，不进客户端）。

**Step 1：数据模型 + 登录**
在 Supabase 里建好上面的表；接入 Supabase Auth，客户端做登录/注册页面。

**Step 2：自然语言生成任务契约**
写一个 Edge Function，接收用户一句话，调用 Claude API 返回结构化 JSON；客户端渲染成可编辑表单 + 确认按钮。

**Step 3：任务列表与本地状态**
SwiftUI 做主界面：待办任务列表、截止时间提醒（本地通知）。

**Step 4：证据提交与AI核验**
客户端用 PhotosPicker 选图 → 上传到 Storage → 触发核验 Edge Function → 轮询或用 Realtime 拿到结果 → 展示 Verified / Need More Proof / Not Verified。

**Step 5：勋章与成就系统**
EXP 累加逻辑、等级计算、Library 页面（按勋章分类回顾历史任务和截图）、每周小结页面。

**Step 6：自用内测**
自己作为第一个用户，用一到两周，重点看："契约生成准不准"、"证据要求是否太麻烦"、"完成后的反馈是否真的有动力感"。

**Step 7：小范围内测**
找 5-10 个同学/朋友用起来，重点收集"AI 生成的验收标准是否合理"和"误判率"两个问题的反馈。

**Step 8：打磨与上架准备**
优化 UI 细节、补充空状态/错误态、准备 Mac App Store 上架素材（如果打算上架）。

**Step 9：迁移到 iOS**
因为 SwiftUI 代码已经跨平台共享，这一步主要是加 iOS target、适配触屏交互（比如相机直接拍照上传）、适配小屏布局，工作量比从零开始小很多。

## 8. 风险与应对

- **AI 误判**：保留三态核验结果，允许用户补交证据或申诉，第一版不设金钱惩罚可以让误判的代价降到最低。
- **证据门槛**：每类任务的默认证据要求尽量选"用户本来就会产生的东西"（LeetCode 的 Accepted 截图、Apple Health 的运动记录），减少"为了证明而额外做的动作"。
- **隐私敏感任务先不做**：订机票这类涉及个人信息的任务证据，放到后续版本，且需要考虑截图脱敏（比如生成契约时提醒用户可以裁剪掉姓名/订单号）。
- **不要一开始就想"完美系统"**：MVP 的意义是尽快验证"这个反馈机制是否真的比打勾更有动力"，这是产品成立与否的核心假设，值得优先验证，而不是优先把技术做全。

## 9. 命名与 Slogan 建议（仅供参考）

- **实锤**（中文语境很贴切，"实锤"本身就是"石锤的证据"的网络流行语，直接对应"用证据说话"的核心概念）
  - Slogan：拿实锤，攒成就
- **Proofed**
  - Slogan：Don't just check it off. Prove it.
- **见证 / Witness**
  - Slogan：让现在的你，见证未来的你完成承诺
